======================================================================
2. PRODUCT VISION
======================================================================

Build an all-in-one alarm, wake-up mission, bedtime audio, and basic
sleep-tracking app. The key differentiator is that users can require
themselves to complete one or more tasks before dismissing an alarm
normally.

Core priorities, in order: 1. Alarm delivery and audio reliability. 2.
Clear alarm creation and management. 3. Mission completion and safe
alarm dismissal behavior. 4. Reboot/time-change/permission recovery. 5.
Accessible, polished UI. 6. Offline sleep sounds and basic sleep
records. 7. Snore-event detection and other advanced functions, with
clear privacy controls.

Never sacrifice alarm reliability for decorative UI or secondary
features.

3. REQUIRED TECHNOLOGY AND ARCHITECTURE
======================================================================

Use: - Kotlin - Jetpack Compose - Material 3 - MVVM - Clean separation
of UI, domain/use cases, repositories, and data sources - Hilt for
dependency injection - Room for structured local data - DataStore for
app preferences - Coroutines and Flow for asynchronous work and state -
Android AlarmManager for scheduled alarms - BroadcastReceiver for
scheduled alarm and system events - CameraX for camera-based missions -
Android sensor APIs for motion/step-related missions, using supported
sensors and fallbacks - Android audio APIs suitable for alarm playback
and sleep audio - Android notification APIs and foreground services only
where required by current platform rules - Unit tests and Android
instrumentation/UI tests where practical

Use current stable compatible dependency versions. Do not invent
dependency versions. Inspect the existing Gradle configuration before
editing it. Keep dependency versions centralized using the project’s
existing version catalog if one exists.

Suggested package structure (adapt to the existing package name if the
repository already has one): - app/ - core/common/ -
core/designsystem/ - core/permissions/ - core/audio/ - data/local/ -
data/repository/ - domain/model/ - domain/repository/ -
domain/usecase/ - feature/home/ - feature/alarms/ - feature/missions/ -
feature/sleep/ - feature/sounds/ - feature/statistics/ -
feature/settings/ - service/alarm/ - receiver/ - worker/ (only for work
that is appropriate for WorkManager; do not use WorkManager for exact
alarm delivery)

Architecture rules: Compose UI -> ViewModel -> Use Case -> Repository ->
Data Source. System alarm delivery must not depend on a screen,
ViewModel, or the app process staying open. The system receiver/service
path must be able to reconstruct the alarm state from persistent
storage.

Keep business logic out of Composables. Use immutable UI state and
one-way data flow. Handle loading, empty, success, permission-denied,
and error states. Avoid giant files and god classes.

7. WAKE-UP MISSIONS — ALL FREE
======================================================================

Implement these eight mission types. Each mission must have a clear
setup flow, instructions, progress, success/failure feedback, and
persisted completion state.

7.1 Math Mission - Generate arithmetic questions. - Difficulty levels:
easy, medium, hard. - Configurable question count. - Validate answers. -
Prevent a blank/invalid answer from counting as correct. - Avoid
repeatedly showing the same trivial questions in one session.

7.2 Memory Mission - Display a sequence of tiles or symbols. - User
repeats the sequence. - Configurable sequence length/difficulty. - Clear
visual/audio accessibility options where practical.

7.3 Shake Mission - Use accelerometer data to detect deliberate
shakes. - Configurable target count and difficulty. - Filter noisy
sensor events and prevent a single movement from counting many times. -
Explain when the required sensor is unavailable.

7.4 Typing Mission - Display a phrase to type. - Configurable phrase
length/difficulty. - Validate the entered phrase according to a
documented normalization policy. - Provide accessible keyboard focus and
text sizing.

7.5 Squat Mission - Use supported device sensors/camera-based estimation
only if feasible and reliable. - Explain setup and placement
instructions. - Calibrate or validate movement to reduce accidental
counting. - Provide a fallback mission if reliable squat detection is
unavailable. - Do not claim accurate exercise recognition without
testing.

7.6 QR/Barcode Mission - Let the user scan and register a QR
code/barcode before the alarm. - At alarm time, require scanning the
registered code. - Validate the scanned value against the saved value. -
Handle camera permission denial and unavailable camera.

7.7 Walking Mission - Count steps using supported step counter/detector
sensors where available. - Request activity-recognition permission if
required by the Android version. - Configure step target. - Explain when
hardware support is missing and provide a fallback.

7.8 Photo Mission - Allow the user to capture/register a reference scene
before the alarm. - At alarm time, capture a new image and compare it
with the reference using a documented, on-device approximate matching
strategy. - Do not require exact pixel equality. - Explain
lighting/framing limitations. - Handle camera permission denial and
unavailable camera. - Do not upload images to a server.

Mission framework: - Allow one or more missions per alarm. - Support a
user-configured combination/all-selected policy where practical. - Allow
difficulty and target settings per alarm. - Save mission
progress/completion. - Returning from a mission must not automatically
dismiss the alarm. - Do not stop the alarm just because a mission screen
opens or the app returns to foreground. - Mission completion must be
verified by domain logic, not by a UI button that blindly marks
success. - Handle app/process recreation without losing mission
configuration. - Offer a clearly accessible emergency stop/escape path
for safety and accessibility. Document that emergency stop can stop
ringing even if a mission is incomplete; do not falsely claim the app
can make the phone impossible to silence.

19. IMPLEMENTATION WORKFLOW FOR ANTIGRAVITY
======================================================================

Follow this workflow:

STEP 1 — INSPECT - Inspect the repository, existing package name, Gradle
setup, SDK levels, dependencies, and current code. - Identify existing
implementations that should be preserved. - Report any major constraints
before making destructive changes.

STEP 2 — PLAN - Create/update a concise implementation plan and task
checklist. - Separate critical alarm reliability work from optional
sleep and audio features. - Identify permissions and Android API
constraints.

STEP 3 — FOUNDATION - Set up architecture, dependency injection, Room,
DataStore, navigation, theme, and shared UI components. - Ensure the
project compiles.

STEP 4 — ALARM MVP - Implement create/edit/delete/enable/disable/repeat
alarms. - Implement scheduling, ringing audio, dismissal, snooze, reboot
recovery, and system permission flows. - Add tests before moving to
advanced missions.

STEP 5 — MISSIONS - Implement each of the eight mission types one by
one. - Add configuration, validation, persistence, and failure
handling. - Do not use fake mission-completion buttons.

STEP 6 — WAKE-UP CHECK - Implement follow-up scheduling and cancellation
safely. - Add statistics and tests.

STEP 7 — SOUNDS AND SLEEP - Implement local sound library, sleep timer,
sleep sessions, reports, and routines. - Then implement snore detection
and recording with privacy controls and supported platform behavior.

STEP 8 — POLISH - Add widget, accessibility, themes, empty/error states,
and statistics charts. - Confirm every screen has functional navigation.

STEP 9 — VERIFY - Run Gradle build and tests. - Fix compile errors,
crashes, lifecycle bugs, and major UI defects. - Review permissions and
Android manifest declarations. - Provide a feature checklist with
statuses: implemented, tested, partially implemented, blocked by
platform/asset requirement. - Document setup instructions, required
audio asset locations/formats, known limitations, and manual QA steps.

Do not attempt to create every feature in one giant code-generation step
if that would compromise correctness. Work incrementally, keep the
project compiling after each milestone, and continue through the
milestones unless blocked. Do not stop after producing only a plan or
mock UI.
